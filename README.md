# VELIX Web Solutions

**1. What this is**

The full VELIX Web Solutions platform, split into two independent halves:

- **The public website** (home, services, portfolio, a project page, news,
  a news article, about, contact) is a **fully static site** — plain HTML/
  CSS/JS plus two generated JSON files and an XML sitemap. It can be
  deployed to GitHub Pages, Cloudflare Pages, Vercel's static hosting, or
  any other static host, and renders completely correctly with **no server
  running at all, anywhere**.
- **The admin dashboard** (`/admin.html`) and the AI sales-chat widget are
  the only parts that need a server. They're served by the same
  self-contained Node.js process as before — no external database, no
  cloud storage account, no third-party backend service. Everything the
  server needs lives on its own disk (SQLite database, uploaded files),
  and the only outside network call it ever makes is to the Anthropic API
  for the chat widget, using your own key.

The link between the two halves is **publishing**: every time you save,
publish, or delete a Project or a News article in the admin dashboard, the
server regenerates `public-data/projects.json`, `public-data/news.json`,
and `sitemap.xml` from SQLite and (best-effort) pushes them to this repo's
git remote, so whatever static host is connected to it redeploys
automatically — see **"Publishing & static hosting"** below. This is the
one thing that has to work for the "server OFF, public site still up"
guarantee to hold; everything else in this section is unchanged from
before.

See `AI_PLATFORM_README.md` for a deeper look at how the AI layer
(gateway, conversation manager, pricing engine, knowledge base, function
calling) is put together.

**2. Architecture**

```
STATIC (no server required)                    ADMIN SERVER (server.js)
-----------------------------                   ----------------------------
index.html, about.html, ...          <---push---   SQLite database   data/velix.db
public-data/projects.json  \                        Local file storage
public-data/news.json       > generated by           uploads/{projects,news,media,general}/
sitemap.xml                /   lib/publish.js        Admin API   /api/admin/*  (session-cookie auth)
assets/, uploads/*                                    Chat / AI API  /api/chat, /api/conversations,
                                                                       /api/leads, /api/quote
Deployed to: GitHub Pages /                          Public API  /api/public/*  (still live, but no
Cloudflare Pages / Vercel                             longer required — see assets/js/store.js)
static hosting / etc.
```

- `server.js` — the admin/AI entry point: serves static files **for local
  development only** (see "Publishing & static hosting" — a real
  deployment does not route public traffic through this process), routes
  `/api/*` requests, and owns the single SQLite connection for the life of
  the process. Also blocks a handful of paths (`data/`, `backups/`,
  `node_modules/`, `lib/`, `scripts/`, `.env*`) from ever being served as
  static files — see "Security" below.
- `lib/publish.js` — reads the current published state out of SQLite and
  writes `public-data/projects.json`, `public-data/news.json`, and
  `sitemap.xml`, then best-effort git-commits and pushes them. Called
  automatically after every publishing admin action (`api/admin/data.js`)
  and once at server startup; runnable by hand with `npm run publish-site`.
- `api/` — one file per HTTP endpoint (admin CRUD, public reads, chat,
  leads, quote, sitemap).
- `lib/` — shared server-side logic: the database layer (`db.js`), admin
  auth (`adminAuth.js`), local file storage (`fileStorage.js`), the publish
  pipeline (`publish.js`, `sitemap.js`), and the AI building blocks
  (`systemPrompt.js`, `tools.js`, `pricingEngine.js`, `conversationState.js`,
  `knowledgeBase.js`).
- `knowledge/` — the AI's knowledge base as structured JSON (company info,
  services, packages, FAQs, policies, process, competitors).
- `assets/` — client-side CSS/JS/images for the public site and admin UI.
- `public-data/` — **generated, and tracked in git** — the static snapshot
  every public page reads (see `assets/js/store.js`). Never edit these
  files by hand; they're overwritten on every publish.
- `scripts/` — one-off maintenance scripts (`backup-db.js`,
  `hash-admin-password.js`, `check.js`, `publish-site.js`).

**3. Requirements**

- Node.js **22.5 or newer** (this project uses Node's built-in
  `node:sqlite` module, which needs that version). Download from
  https://nodejs.org.

**4. Install**

```
npm install
```

This installs the only two runtime dependencies: `@anthropic-ai/sdk` (AI
chat) and `bcryptjs` (admin password hashing).

**5 & 6. Environment setup — creating `.env.local`**

The server reads all configuration from a single `.env.local` file in the
project root, which is **never committed to git** (see `.gitignore`).
There are two ways to create it:

- **Windows, automated (recommended):** double-click `RUN-SETUP-VELIX.bat`
  (or run `SETUP-VELIX.ps1` in PowerShell — no Administrator rights
  needed). It checks your Node/npm install, runs `npm install` if needed,
  creates the required folders, asks you interactively for your admin
  email, a new admin password, and your Anthropic API key — none of which
  are ever echoed to the screen — hashes the password and generates a
  session secret for you, writes everything to `.env.local`, and starts
  the server.
- **Manual (any OS):** copy `.env.example` to `.env.local` and fill in:
  - `ADMIN_EMAIL` — the email you'll log into the admin dashboard with.
  - `ADMIN_PASSWORD_HASH` — generate with:
    ```
    node scripts/hash-admin-password.js "your-new-password"
    ```
    and paste the printed hash (starts with `$2a$` or `$2b$`) into
    `.env.local`. Never store the plain password anywhere.
  - `ADMIN_SESSION_SECRET` — generate with:
    ```
    node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
    ```
  - `ANTHROPIC_API_KEY` — from https://console.anthropic.com, for the AI
    chat widget (see "AI configuration" below). Leave blank to run the
    site with AI chat disabled.
  - `PORT` / `HOST` — defaults (`3000` / `0.0.0.0`) are fine for most
    setups; see "Windows server deployment" below if you want this
    reachable from other devices on your network.

**7. Start the server**

```
npm start
```

(`npm run dev` runs the exact same thing — both just run `node server.js`.)

On Windows, you can instead double-click **`START-VELIX-SERVER.bat`**,
which verifies dependencies, refuses to start a second copy if one is
already running on the configured port, and starts the server the same
way.

Then open **http://localhost:3000/** (or whatever `PORT` you set) for the
website, and **http://localhost:3000/admin.html** to sign in to the admin
dashboard with the `ADMIN_EMAIL` / password from setup.

**8. Database location**

`data/velix.db` (plus its SQLite WAL files) — every project, news article,
media record, setting, lead, conversation, and activity-log entry. Created
automatically the first time the server starts; there is nothing to set up
by hand, and a fresh clone/install starts with an empty database. Never
committed to git.

**9. Upload storage**

`uploads/projects/`, `uploads/news/`, `uploads/media/`, `uploads/general/`
— served back out at `/uploads/<bucket>/<filename>`. All four are created
automatically on first run. Like `data/velix.db`, `uploads/` is
**`.gitignore`d on `main`** — it never enters `main`'s git history. But
every image/video a published Project or News article references still
has to be part of the static deploy for it to keep showing up with the
server off, so `lib/publish.js` copies `uploads/` straight into the
separate `gh-pages` branch on every publish, alongside `public-data/*.json`
(see section 10). Nothing private lives here: only files an admin has
actually uploaded through the dashboard for public content.

**10. Publishing & static hosting (the public site works with the server OFF)**

This is the piece that makes the guarantee in section 1 real: the public
website must keep working when this Node process is not running at all.

*How it works:* every time you save/publish/unpublish/delete a Project or
News article in `/admin.html`, `api/admin/data.js` writes to SQLite (as
always) and then calls `lib/publish.js`, which:
1. Reads the current published, non-deleted rows straight from SQLite.
2. Writes them to `public-data/projects.json`, `public-data/news.json`,
   and `sitemap.xml` at the project root — plain static files, not API
   responses. (These are `.gitignore`d on `main` — they're build output,
   regenerated from SQLite every time, not application source.)
3. Builds a **separate `gh-pages` branch** — using a disposable git
   worktree under the OS temp directory, so nothing here ever touches
   `main`'s working tree — containing **only** the explicit allowlist in
   `lib/publish.js`'s `PUBLIC_ALLOWLIST`: the public `*.html` pages,
   `assets/` (minus `assets/js/admin-api.js`, which no public page loads),
   `uploads/`, `public-data/`, `sitemap.xml`, and the hosting-config files
   (`CNAME`, `robots.txt`, `_redirects`, `vercel.json`, the Search Console
   verification file). `server.js`, `lib/`, `api/`, `scripts/`,
   `package.json`/`package-lock.json`, `data/`, `.env*`, `admin.html`,
   `README.md`, and every other backend/dev file are **never** copied —
   not hidden, not blocked by an app-level check, genuinely absent from
   that branch's file tree, so no static host serving it can expose them.
4. Commits and pushes that branch (best-effort — see below). `main` is
   never committed to as part of a publish; it stays exactly what you
   edit by hand, the full application source.

`assets/js/store.js` (loaded by every public page) reads
`public-data/projects.json` / `public-data/news.json` directly — it never
calls this server's API to render a public page. `project.html` and
`news-post.html` read the same in-memory cache `store.js` already
populated, so they need no server either. The contact form and the AI
chat widget still call the server when actively used (sending a message,
submitting the form) — both already degrade gracefully if the server is
unreachable (see `assets/js/script.js`'s contact handler and
`assets/js/chat-widget.js`'s local fallback), so neither can ever break
page load.

*Deploying the static half:* pick one static host and point it at the
**`gh-pages` branch** (not `main`) of this repository — each one
redeploys automatically on every push `lib/publish.js` makes, with no
build step or CI/workflow file needed, and none of them ever sees this
repo's backend source because that branch never contains it:
- **GitHub Pages** — repo Settings → Pages → "Deploy from a branch" →
  `gh-pages` / `/ (root)`. (This repo's `CNAME` file, carried onto
  `gh-pages` too, already points it at `velixweb.xyz`.)
- **Cloudflare Pages** — "Connect to Git", pick this repo, production
  branch `gh-pages`, build command empty, output directory `/` (root).
- **Vercel** (static hosting, not serverless functions for the public
  site) — "Import Git Repository", pick branch `gh-pages`, framework
  preset "Other", no build command.

Whichever you pick, DNS for `velixweb.xyz` should point at that host, not
at your own machine — that is what actually removes the "my laptop has to
stay on" requirement. The admin server keeps running wherever you already
run it (see "Windows server deployment" below); it no longer needs to be
reachable from the internet as `velixweb.xyz` at all, only to yourself
while you're using `/admin.html`.

*Git push credentials:* `lib/publish.js` runs plain `git push` using
whatever remote + credentials are already configured in this working
copy (the normal case if you can already push to this repo by hand from
this machine) — it pushes to `gh-pages` specifically, `main` is
untouched. If that's not set up yet, publishing still regenerates every
file correctly on disk and commits locally to `gh-pages` every time; only
the push to the remote is skipped until you configure git push access and
run `npm run publish-site` once by hand (or set `GIT_AUTO_PUSH=false` in
`.env.local` if you'd rather always review and push yourself). A failed
git push is logged and returned to the admin dashboard's response but
never fails the save itself — the database write already succeeded
regardless.

*First-time setup:* right after deploying this change, run
`npm run publish-site` once by hand — this creates the `gh-pages` branch
(if it doesn't exist yet) seeded with every currently published
Project/News item and every image already in `uploads/`, and pushes it
(ongoing publishes after that only need to carry whatever actually
changed). Point your chosen static host at `gh-pages` as described above
either before or after running this — whichever order, the site is live
once both are done.

**11. Backup system**

```
npm run backup
```

Copies `data/velix.db` to a timestamped file under `backups/`, e.g.
`backups/velix-2026-09-10-120000.db`. Safe to run at any time, including
while the server is running — it never deletes or modifies the live
database. Run it on a schedule (Windows Task Scheduler, or just by hand
periodically) for real protection against disk failure/corruption.

To back up uploaded files, just copy the `uploads/` folder — it's plain
files, so any normal backup tool (or copying it to an external drive / a
cloud sync folder) works.

**12. Admin setup**

There is one admin account, configured entirely through `.env.local` —
there is no "sign up" flow and no admin credential anywhere in
HTML/CSS/JS. See `lib/adminAuth.js` and `api/admin/*.js` for how the
session-cookie auth works. To change the admin password later, generate a
new hash (`node scripts/hash-admin-password.js "new-password"`) and
replace `ADMIN_PASSWORD_HASH` in `.env.local`, then restart the server.

**13. AI configuration**

The AI chat widget (`api/chat.js`) talks to Claude through the official
`@anthropic-ai/sdk`, using the key you set as `ANTHROPIC_API_KEY` in
`.env.local`. The key is read only on the server and never reaches
client-side JavaScript. If it's left blank, the rest of the site works
normally — the chat widget shows a "not configured" state instead of
erroring. See `AI_PLATFORM_README.md` for how the AI layer is structured
(system prompt, tools/function-calling, pricing engine, conversation
state, knowledge base) — none of that logic needs to change to run this
project; it's documentation, not setup.

**14. Windows server deployment (the admin server only — see section 10 for the public site)**

**One-step setup:** run `RUN-SETUP-VELIX.bat` (see "Environment setup"
above) — it configures `.env.local` and starts the server for normal,
day-to-day use.

**Run permanently (survive reboots/logout):** run
`INSTALL-VELIX-SERVICE.ps1` once (right-click → "Run with PowerShell", or
double-click it — it elevates itself and asks for one UAC confirmation).
It:

1. Adds a Windows Firewall inbound rule for TCP `3000`, scoped to your
   **Private/Domain** network only (never Public, never the internet) —
   see "Security" below.
2. Registers a Scheduled Task named **VELIX Server** that starts
   `node server.js` automatically the next time you log into Windows, with
   its output appended to `logs\server.log`.

It's safe to re-run — it replaces its own rule/task rather than duplicating
them. To start the server immediately without logging out/in:
`Start-ScheduledTask -TaskName 'VELIX Server'` in an elevated PowerShell, or
just double-click `START-VELIX-SERVER.bat`. To remove autostart later, run
`UNINSTALL-VELIX-SERVICE.ps1` (or `Unregister-ScheduledTask -TaskName
'VELIX Server'`).

If you'd rather run it before any user logs in (e.g. an unattended machine
that reboots with nobody signed in), change the task's trigger to
"At startup" and its "run as" account to `SYSTEM` in Task Scheduler — the
default logon-trigger setup above needs no stored credentials and is the
right choice for a normal desktop that you log into.

Other valid options if you'd rather not use Task Scheduler: a process
manager such as [PM2](https://pm2.keymetrics.io/) (`pm2 start server.js
--name velix`, then `pm2 save` + `pm2-startup`), or **NSSM** (the
Non-Sucking Service Manager) to register `node server.js` as a genuine
Windows service.

Whichever you choose, `HOST=0.0.0.0` in `.env.local` (the default) makes
the server reachable from other devices on your local network, not just
this PC — it does **not** by itself make it reachable from the internet.

**Connecting a domain to the ADMIN server:** as of section 10 above,
`velixweb.xyz` itself should point at your static host (GitHub Pages /
Cloudflare Pages / Vercel), not at this machine — that's what lets the
public site survive this machine being off. If you still want to reach
`/admin.html` over the internet rather than only on your local network,
give the admin server its own separate hostname (a subdomain such as
`admin.velixweb.xyz`, or just its LAN IP if you never need to log in from
outside) and point DNS/tunnel at that instead of the bare domain. The two
options below are for exposing *this admin server* under whichever
hostname you pick — not for the public site, which no longer needs either
of them:

- **Option A — router port forwarding + reverse proxy:** give the PC a
  stable address (Dynamic DNS or a static IP from your ISP), forward the
  port through your router, point a DNS `A`/`CNAME` record at it, and put
  a reverse proxy ([Caddy](https://caddyserver.com/) or nginx) in front on
  80/443 to handle TLS — never expose the raw Node process on the public
  internet without TLS in front of it.
- **Option B — Cloudflare Tunnel:** install `cloudflared`, run
  `cloudflared tunnel login` / `create` / `route dns`, and forward to
  `http://localhost:3000`. Cloudflare terminates HTTPS for you and no
  router port ever needs to open — generally the simpler and safer option
  for a home/office PC.

Either way, the server itself needs to already be running permanently on
the PC first (see above).

**15. Security**

Read this before putting real traffic or real customer data through this
server.

- **Never commit `.env.local`.** It holds your admin password hash,
  session-signing secret, and Anthropic API key. `.gitignore` excludes it
  by pattern (`.env.*`, with only `.env.example` allowed through) — don't
  override that, and don't paste its contents into issues, commits,
  screenshots, or chat.
- **If any secret in `.env.local` is ever exposed** (committed by
  accident, pasted somewhere public, etc.), rotate it immediately:
  generate a new `ADMIN_PASSWORD_HASH` and a new `ADMIN_SESSION_SECRET`
  (invalidates all existing admin sessions), and revoke/reissue the
  Anthropic API key from the console.
- **The SQLite database is never exposed over HTTP.** `data/`, `backups/`,
  `node_modules/`, `lib/`, `scripts/`, and any `.env*` file are not served
  as static files (`server.js`'s `STATIC_DENY_TOP_LEVEL`/`isDeniedStaticPath`
  — request one and you get a 403, not the file), and path-traversal
  attempts against the static file server and the upload routes are
  rejected. Admin API routes require a valid session cookie; there is no
  way to query SQLite directly from a request. In production, though, none
  of this matters for the public site anyway — see section 10: the
  public site is deployed as static files on a static host that never runs
  this Node process (and therefore never has `data/velix.db` on it at
  all), so there is nothing for this server to accidentally expose to a
  public visitor in the first place.
- **The git push credentials `lib/publish.js` uses are whatever this
  machine already has** (its own git config / credential manager) — this
  code never reads, stores, or transmits a token itself. If you'd rather
  use a dedicated fine-grained GitHub token instead of your own account's
  credentials, configure it the normal git way (a credential helper, or a
  remote URL containing the token) — do not paste a token into any file in
  this repo.
- **Secrets never reach client-side JavaScript.** `ANTHROPIC_API_KEY`,
  `ADMIN_PASSWORD_HASH`, and `ADMIN_SESSION_SECRET` are read only inside
  server-side files (`server.js`, `lib/*.js`, `api/*.js`) and are never
  interpolated into any HTML/CSS/JS sent to the browser.
- **This is genuine self-hosting** once you connect a real domain: keeping
  Windows, Node, and dependencies updated, keeping `.env.local` private,
  backing up `data/velix.db` regularly, and keeping a TLS-terminating
  reverse proxy (or Cloudflare Tunnel) in front before real visitors are
  involved are all your responsibility as the operator, not something this
  codebase can enforce for you.
- **Firewall scope:** `INSTALL-VELIX-SERVICE.ps1` only ever opens the
  single port this server uses, and only on the Private/Domain network
  profiles — never Public, never by disabling Windows Firewall itself.
  Don't widen this without understanding what you're exposing.

## Development checks

```
npm run lint
```

(same as `npm test`) — checks every `.js` file for syntax errors, every
`.html` file for balanced `<script>` tags and Windows-style backslash
paths, that no Supabase (or other removed cloud-database) reference has
crept back in, and that no secret-shaped string is hardcoded in source.
